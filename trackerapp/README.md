# Tracker (Android)

A very simple standalone Android app for the same live-tracking flow as `web/`, for when you'd
rather both sides use an app instead of a browser page:

- **Home screen** (sender): pick a destination, tap **Generate & share via WhatsApp** — it creates
  a trip and opens WhatsApp with a tracking link pre-filled.
- **Recipient screen**: opened automatically when someone taps that link (if this app is
  installed). Shows a consent screen, then - only after they tap **Share my location** - starts
  sending live position updates and shows their own map + ETA, with a **Stop sharing** button.

It's a separate app (own package, own launcher icon) alongside the existing `Yalla Muv TMS` app in
this repo - unrelated to tariffs/CRM/invoices, install it independently.

## It reuses the web app's backend

This app is **just another client of the same Firestore `tracking_sessions` collection** the
`web/` app uses (see `/firestore.rules`). Same schema, same security rules, same 24h expiry. That
means:

- Links generated by this app or by the web dashboard are interchangeable.
- You only need to set up **one** Firebase project, shared by both `web/` and this app.
- Deploy `web/` first (see `web/README.md`) - this app's tracking links point at that Firebase
  Hosting domain, and if the app isn't installed the same link still opens as a normal web page.

No Google Maps API key anywhere: the map is OpenStreetMap tiles via osmdroid, and routing/ETA is
the free public OSRM server - both keyless, matching `web/`'s stack.

## One-time setup

1. **Deploy `web/` first** (see `web/README.md`) and note your Hosting domain, e.g.
   `your-project.web.app`.
2. **Register this Android app in the same Firebase project**: Firebase console → Project
   settings → Add app → Android. Package name: `com.aistudio.yallamuv.tracker`. Download the
   generated `google-services.json` and place it at `trackerapp/google-services.json`.
   (Without this file the app still builds - `googleServices.missing.passthrough=true` in
   `gradle.properties` - but Firestore calls will fail until it's added.)
3. **Set the hosting domain** in `trackerapp/build.gradle.kts`: replace
   `REPLACE_WITH_YOUR_FIREBASE_HOSTING_DOMAIN` (in `defaultConfig`) with your real domain from
   step 1, e.g. `your-project.web.app`. This is what tracking links point to and what the app's
   deep-link filter matches.
4. **(Optional but recommended) Wire up App Links** so tapping a link in WhatsApp opens this app
   directly instead of a browser tab:
   - Get your signing certificate's SHA-256 fingerprint. For local debug builds, from the repo
     root: `keytool -list -v -keystore debug.keystore -alias androiddebugkey -storepass android -keypass android`
     (look for the `SHA256:` line). For release builds, run the same against your upload keystore.
   - Paste the fingerprint(s) into `web/.well-known/assetlinks.json`, replacing the two
     `REPLACE_WITH_...` placeholders (you can list both debug and release fingerprints in the
     array).
   - Redeploy hosting so the file is live: `firebase deploy --only hosting` (from the repo root).
   - Skip this step if you'd rather not bother - tracking links still work fine as a normal web
     page in that case, since `web/track.html` already handles the recipient flow.

## Build & run

This module has no committed Gradle wrapper (same as the existing `app` module) - open the repo
root in Android Studio, let it sync, and run the `trackerapp` configuration on a device/emulator.
If you'd rather use the command line, generate a wrapper once (`gradle wrapper`) and then:

```
./gradlew :trackerapp:assembleDebug
```

### Testing the recipient flow without setting up App Links yet

While you're still developing, you can jump straight to the recipient screen with a plain
custom-scheme link (no hosting/asset-link setup needed) - grab a session id from a trip you
created in the app, then:

```
adb shell am start -a android.intent.action.VIEW -d "yallamuvtracker://track?id=SESSION_ID"
```

## Limits (by design, to keep this simple)

- **Location updates only happen while this app is open and in the foreground.** There's no
  background location service - that would need the `ACCESS_BACKGROUND_LOCATION` permission plus
  a persistent foreground-service notification, and Play Store review for background location use.
  Same constraint the web version has for the same underlying reason (mobile OSes restrict
  background location access by design).
- **The sender's "Your tracking links" list is local to that device** (SharedPreferences, no
  accounts) - exactly like the web dashboard's use of `localStorage`. Generating links from a
  different device/install gives you a separate list.
- Trips still expire after 24 hours and follow the same trust model as the web app: the link's id
  is the credential, nobody can enumerate sessions, and a closed/declined/arrived trip can never
  be reopened (see `/firestore.rules`).
